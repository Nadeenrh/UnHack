# Nightwatch database

MySQL 8.4 is the single system of record: organizations, users, memberships, monitored assets, alerts, incidents, evidence, agent runs, policies, actions/approvals and the audit log. Raw telemetry stays in Wazuh. The Python agent service stores nothing.

| Path | What it is |
|---|---|
| `init/001_schema.sql` | The schema. Non-destructive: never drops a table or a row. |
| `init/002_dev_fixtures.sql` | Demo data, every incident labelled `fixture`. Generated by `tools/fixtures/build_fixtures.py`; don't edit by hand. |
| `init/003_add_healthcare_sector.sql` | Adds the `healthcare` sector. Run it by hand on an existing database (command inside the file). |
| `reset/RESET_DEV_ONLY.sql` | Wipes the database. Manual, dev only, never automatic. |

## Start it

```bash
cp .env.example .env.local      # then fill in values
docker compose --env-file .env.local -f docker-compose-dev.yml up -d db
```

On the first start (empty volume) MySQL runs `init/` in order. After that it never runs them again, so restarts and `docker compose down` keep your data.

## Start over (dev only)

```bash
docker compose -f docker-compose-dev.yml down
docker volume rm nightwatch_nightwatch_mysql   # name = <folder>_nightwatch_mysql; check with: docker volume ls
docker compose --env-file .env.local -f docker-compose-dev.yml up -d db
```

## Tenancy, enforced twice

Every customer-owned table has `org_id`. The app scopes every query by the org from the session, never from the request. As a second layer, child tables reference their parent by `(id, org_id)`, so MySQL itself refuses to attach an action, evidence row, alert or asset to another org's incident.

## Approvals

Approving an action is one conditional update:

```sql
UPDATE actions
SET status = 'approved', decided_by = ?, decided_at = NOW(3)
WHERE action_id = ? AND org_id = ? AND target = ? AND status = 'awaiting_approval';
```

Zero rows updated means refuse: wrong org, the target changed since it was reviewed, or someone already decided. `idempotency_key` is unique, so the same action can't be created or executed twice.

## Audit log

Triggers block `UPDATE` and `DELETE` on `audit_log`. That makes it tamper-evident to the application. A database administrator can still drop the triggers, so don't call it tamper-proof.
